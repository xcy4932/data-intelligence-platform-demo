**留存分析 PRD**

**1. 功能定位**

留存分析用于回答：

用户在完成某个起始行为后，是否会在之后继续完成某个关键行为。

例如：

用户注册后，第 1 天、第 3 天、第 7 天是否再次登录；用户首次下单后，7 天内是否再次下单；用户参与某活动后，是否继续发生付费、观看广告、进入游戏、完成任务等行为。

本功能不是只做“新用户留存”，而是一个自定义留存分析工具。用户可以自由配置：

起始事件、回访事件、事件过滤条件、关联属性、用户筛选、分组、留存窗口、时间粒度、留存/流失模型、同时显示指标、图表展示、明细表、导出、保存分析、保存到看板。

明确区分“基本留存”和“自定义留存”：新用户/活跃用户留存是预置口径，自定义留存允许用户自行指定起始事件和回访事件。

**3. 核心概念与计算口径**

**3.1 起始事件**

起始事件是用户进入某个分析起点的行为。

例如：

注册

首次登录

完成新手引导

观看广告

进入游戏房间

首次下单

领取优惠券

起始事件用于确定“起始人群”。

同一统计周期内，同一用户多次触发同一个起始事件时，默认只计入一次。DataFinder 常见问题中也说明，多个相同起始事件只计算一次。

**3.2 回访事件**

回访事件是用户在起始事件之后需要再次触发的行为。

例如：

登录

进入游戏

观看广告

再次下单

完成支付

阅读文章

参与活动

回访事件必须发生在起始事件之后。

如果起始事件和回访事件发生在同一时间戳，默认不计入留存。DataFinder 文件中说明，当日/当周/当月留存计算时，回访事件时间须晚于起始事件，同时发生不计入留存。

**3.3 留存率**

基础公式：

$$
\text{RetentionRate}*{t,w}=\frac{\text{RetainedUsers}*{t,w}}{\text{StartUsers}\_{t}}\times 100%。
$$

其中：

| **字段** | **含义** |
| --- | --- |
| StartUsers\_t | 在起始日期 t 触发起始事件的去重用户数 |
| RetainedUsers\_t,w | 起始日期 t 的用户中，在留存窗口 w 内触发回访事件的去重用户数 |
| RetentionRate\_t,w | 起始日期 t 在窗口 w 的留存率 |

**3.4 流失率**

流失率用于查看用户在起始事件后连续未发生回访事件的比例。

基础公式：

$$
\text{ChurnRate}*{t,n}=\frac{\text{UsersWithoutReturnFromDay1ToDayN}*{t}}{\text{StartUsers}\_{t}}\times 100%。
$$

DataFinder 对流失用户的定义是：从触发起始行为事件后的第 2 天开始，连续多天没有发生后续事件才认为是流失用户；第 N 日流失率等于第 2 日到第 N 日每天都无回访事件的人数除以当日起始事件人数。

本产品实现时，为了兼容神策口径，内部字段命名使用：

churnStartOffset = 1

含义是：从起始事件后的第 1 个完整周期开始判断流失。

页面文案上根据时间粒度展示为：

第 1 日流失 / 第 2 日流失 / 第 7 日流失

**4. 留存模型设计**

**4.1 特定日期留存**

用户在起始行为后的第 N 天、周、月发生回访事件，即计为第 N 周期留存。

适用于：

次日留存

3 日留存

7 日留存

30 日留存

第 2 周留存

第 1 月留存

配置项：

| **字段** | **类型** | **示例** |
| --- | --- | --- |
| modelType | enum | fixed\_date |
| granularity | enum | day / week / month |
| windows | number[] | [1, 3, 7, 14, 30] |
| includeDay0 | boolean | false |

当 granularity = day，windows = [1, 3, 7] 时：

| **窗口** | **计算范围** |
| --- | --- |
| Day1 | 起始事件发生后的第 1 天 |
| Day3 | 起始事件发生后的第 3 天 |
| Day7 | 起始事件发生后的第 7 天 |

**4.2 自定义区间留存**

用户在起始行为后的某个自定义时间区间内发生回访事件，即计为该区间留存。

例如：

| **区间** | **业务含义** |
| --- | --- |
| Day1-Day3 | 新手兴趣探索期 |
| Day4-Day7 | 新手激活期 |
| Day8-Day30 | 长期粘性观察期 |

DataFinder 文件也给了类似例子：1～3 天用于推荐策略兴趣刺探，4～7 天通过积分/会员政策引导完善信息，8～30 天通过分享、点赞、关注建立用户连接。

配置项：

customWindows: Array<{

id: string;

name: string;

startOffset: number;

endOffset: number;

unit: "day" | "week" | "month";

}>

示例：

[

{

"id": "w1",

"name": "新手探索期",

"startOffset": 1,

"endOffset": 3,

"unit": "day"

},

{

"id": "w2",

"name": "激活期",

"startOffset": 4,

"endOffset": 7,

"unit": "day"

},

{

"id": "w3",

"name": "长期粘性期",

"startOffset": 8,

"endOffset": 30,

"unit": "day"

}

]

校验规则：

| **校验项** | **规则** |
| --- | --- |
| startOffset | 必须 >= 0 |
| endOffset | 必须 >= startOffset |
| 区间重叠 | 默认允许，但给出提示；可在项目设置中限制不允许重叠 |
| 区间数量 | 默认最多 10 个 |
| 最大窗口 | 日粒度最大 120 天，周/月粒度按项目配置 |

DataFinder 中提到，第 2 日至 n 日留存最多可查看 Day120。

**4.3 连续留存**

连续留存是高级模型。

定义：

用户从起始行为后开始，在连续 N 天、周、月内，每一个周期都触发了回访事件。

例如：

连续 7 天阅读小说

连续 3 周登录 App

连续 2 个月完成购买

配置项：

continuousRetention: {

enabled: boolean;

includeStartDay: boolean;

window: number;

unit: "day" | "week" | "month";

}

规则：

| **配置** | **含义** |
| --- | --- |
| includeStartDay = true | 起始行为当天也必须触发回访事件 |
| includeStartDay = false | 从起始行为后的第 1 个周期开始判断 |
| window = 7 | 连续 7 个周期都要满足 |

默认不开启。页面可展示为：

高级留存模型：连续留存

**5.4 关联属性配置**

**功能说明**

关联属性用于要求起始事件和回访事件的某个属性值一致。

例如：

| **场景** | **起始事件** | **回访事件** | **关联属性** |
| --- | --- | --- | --- |
| 同商品复购 | 浏览商品 | 购买商品 | product\_id |
| 同页面回访 | 浏览页面 | 浏览页面 | page\_title |
| 同活动回访 | 参与活动 | 完成活动任务 | campaign\_id |

DataFinder 文件明确说明，关联属性要求起始事件和回访事件的属性值保持一致，且两个关联属性须有值、类型一致。

**字段结构**

relationProperties: Array<{

id: string;

startProperty: string;

returnProperty: string;

propertyType: "string" | "number" | "boolean" | "datetime";

}>

**校验规则**

| **校验项** | **规则** |
| --- | --- |
| 属性类型 | 起始属性与回访属性类型必须一致 |
| 空值 | 任一侧属性为空时，该事件不参与关联留存计算 |
| 多个关联属性 | 多个关联属性之间为 AND |
| 分组限制 | 开启关联属性后，默认只允许按起始事件属性、用户属性、用户标签、用户分群分组 |

**SQL 逻辑示意**

start\_events.user\_id = return\_events.user\_id

AND return\_events.event\_time > start\_events.event\_time

AND start\_events.product\_id = return\_events.product\_id

**9. 时间范围与时间粒度**

**9.1 时间范围**

页面时间选择的是“起始事件发生时间范围”。

例如用户选择：

2026-05-01 至 2026-05-07

留存窗口选择 Day7，则系统实际需要查询：

起始事件：2026-05-01 至 2026-05-07

回访事件：2026-05-01 至 2026-05-14

也就是说，回访事件查询范围需要根据最大留存窗口自动向后延展。

**9.2 时间粒度**

| --- | --- |
| 日 | 按自然日统计 |
| 周 | 按自然周统计，默认周一开始 |
| 月 | 按自然月统计 |

**10. 同时显示指标**

**10.1 功能说明**

同时显示指标用于在留存率之外，统计留存用户在留存窗口内产生的业务指标。

例如：

留存用户充值金额

留存用户人均充值金额

留存用户广告观看次数

留存用户订单金额

留存用户 LTV

DataFinder 文件中也提到，可在用户行为留存指标分析基础上，同时分析业务目标维度的分析指标，例如人均下单金额。

**支持指标类型**

| **指标** | **计算逻辑** |
| --- | --- |
| 总次数 PV | 事件发生次数 |
| 总人数 UV | 事件触发人数 |
| 人均次数 PV/UV | 事件次数 / 回访人数 |
| 求和 SUM | 某属性值之和 |
| 人均值 SUM/UV | 某属性值之和 / 回访人数 |
| 阶段累计总和 CUMSUM | 截至当前窗口累计属性值之和 |
| 阶段累计人均值 CUMSUM/UV | 累计属性值之和 / 回访人数 |
| 阶段累计人均值 CUMSUM/FUV | 累计属性值之和 / 起始人数 |

这些算子与 DataFinder 文档中的分析指标算子一致。

**字段结构**

extraMetrics: Array<{

id: string;

eventName: string;

displayName: string;

aggregator:

| "PV"

| "UV"

| "PV\_UV"

| "SUM"

| "SUM\_UV"

| "CUMSUM"

| "CUMSUM\_UV"

| "CUMSUM\_FUV";

propertyName?: string;

filters?: FilterGroup;

}>

**LTV 计算**

如果用户选择：

事件：支付成功

属性：支付金额

指标：阶段累计人均值 CUMSUM/FUV

则可计算该起始 cohort 在不同留存窗口内的人均价值。

公式：

$$
\text{LTV}*{t,w}=\frac{\sum \text{PaymentAmount}*{t,0\rightarrow w}}{\text{StartUsers}\_{t}}。
$$

**限制**

| **场景** | **规则** |
| --- | --- |
| 开启属性分组 | 默认不支持同时显示指标，除非后端查询引擎支持 |
| 指标过多 | 默认最多 5 个 |
| 指标事件无数据 | 表格显示 0，不显示空 |
| SUM 类指标未选择属性 | 禁止运行查询 |

| C-003 | 去重逻辑 | 同一周期同一用户只计一次起始人数 |
| C-004 | 关联属性 | 仅属性值一致时计入留存 |
| C-005 | 流失率 | 连续未回访用户计入流失 |
| C-006 | 自定义区间 | 用户在区间内任意一次回访即计入 |
| C-007 | 连续留存 | 每个连续周期均触发才计入 |
| C-008 | LTV | 阶段累计金额 / 起始人数 |
